# SR 11-7: Model Risk Management for AI agents

**Source:** Federal Reserve Supervisory Letter [SR 11-7 / OCC 2011-12](https://www.federalreserve.gov/supervisionreg/srletters/sr1107.htm) (April 4, 2011), *Supervisory Guidance on Model Risk Management*. Authoritative text: the Federal Reserve and OCC publications.

**Scope:** SR 11-7 is US banking supervisory guidance on managing the risk of using quantitative models in business decisions. AI agents that take actions on behalf of a bank fall under the same supervisory expectations to the extent that the agent's actions constitute model output or are governed by model output.

This document maps the four SR 11-7 framework areas to the Provenex receipt field or operational artifact that produces evidence for them. The mapping is intended for banks deploying AI agents who need to extend an existing SR 11-7 program to cover those agents.

## III. Model Development, Implementation, and Use

> An effective process to develop, implement, and use models is the foundation of model risk management.

SR 11-7 section III emphasises documentation of model purpose, methodology, data, and limitations.

| SR 11-7 expectation | Provenex artifact |
| --- | --- |
| Documentation of model use cases | `actions[*].name`, `actions[*].operation`, `actions[*].target_system` per receipt. The deployed agent's actual use is recorded per call. |
| Limitations and assumptions documented | `policy.*.policy_id` and `policy.*.policy_version_hash` on every receipt. The policy file itself documents the operational constraints; the hash proves which version was in effect when. |
| Approval prior to use | Receipt signature is the producer's approval mark per call. The pre-deployment policy approval is upstream of the receipt; Provenex makes the approval visible per event. |

## IV. Model Validation

SR 11-7 section IV is the load-bearing one for an evidence layer. It identifies three core elements:

> The activities of model validation are best summarized in the following three core elements:
> - Evaluation of conceptual soundness, including developmental evidence;
> - Ongoing monitoring, including process verification and benchmarking;
> - Outcomes analysis, including back-testing.

### IV.A Evaluation of conceptual soundness

Conceptual soundness is a pre-deployment activity. Receipts do not contribute directly; the policy file (which Provenex consumes) is the artifact that captures the soundness review's output.

### IV.B Ongoing monitoring

> Ongoing monitoring confirms that the model is appropriately implemented and is being used and is performing as intended.

| Monitoring expectation | Provenex artifact |
| --- | --- |
| Process verification (model is being used as intended) | Receipts show every call: caller, action, parameters hash, outcome. Aggregating by `caller_hash` and `actions[*].name` reveals usage drift. |
| Performance monitoring | `policy.*.decisions[*].decision` aggregated over time. A spike in denies on a previously-allow-heavy rule is a monitoring signal. |
| Process verification (inputs, calculations, reports correct) | `policy.*.decisions[*].inputs_hash` plus `policy.*.decisions[*].inputs` (when not redacted). The signed payload commits to the inputs that produced the decision. |
| Periodic re-verification | `provenex selftest` confirms the verification pipeline matches the documented algorithm against the installed binary. Scheduled as a cron job, this provides ongoing process verification. |

### IV.C Outcomes analysis

> Outcomes analysis compares model outputs to corresponding actual outcomes.

| Outcomes-analysis expectation | Provenex artifact |
| --- | --- |
| Recorded outputs | `output.hash` per receipt (SHA-256 of the LLM response). The receipt commits to the bytes that came out; the operator chooses whether to also store verbatim outputs separately. |
| Back-testing against actual outcomes | Trajectory archive: `provenex audit --trajectory <dir>` replays a complete agent run end-to-end against the recorded policy. Pairing receipt archives with downstream business outcomes is the bank's back-test. |
| Benchmarking | The `policy.*.policy_version_hash` boundary makes regime changes detectable: outcomes before and after a hash change can be compared as separate populations. |
| Replay against a candidate new policy | `provenex policy simulate` (commercial; see [`docs/policy.md`](../policy.md)) replays the historical receipt trajectory against a candidate new policy and surfaces what would have changed. |

## V. Governance, Policies, and Controls

> A strong governance framework provides explicit support and structure to risk management functions through policies defining relevant risk management activities, procedures that implement those policies, allocation of resources, and mechanisms for evaluating whether policies and procedures are being carried out as specified.

| Governance expectation | Provenex artifact |
| --- | --- |
| Policies defining risk management activities | The YAML policy file is the machine-readable policy. The verification and access-control halves cover data integrity and authorisation; the tool-call admission half covers action authorisation. |
| Procedures implementing those policies | The `verify_chunks` and `admission_check` entry points implement the policy in code. Source is open; auditors can review the implementation. |
| Mechanism for evaluating whether policies are being carried out | The receipt is the per-event evaluation record. `provenex audit` and the OCSF SIEM export are the aggregate evaluation surface. |
| Independent review | The pure-stdlib reference verifier in [`docs/regulator_verification.md`](../regulator_verification.md) lets a model risk function independently verify receipts without relying on the operator's Provenex deployment. |

## VI. Conclusion: regulator-facing artifact bundle

SR 11-7 section II.2 ("Effective Challenge") emphasises independent challenge by parties separate from those who developed and use the model. The artifact bundle that supports independent challenge for a Provenex-governed agent is:

| Bundle component | Path |
| --- | --- |
| Policy file (verification + access_control + tool_call_control halves) | The deployed YAML, hashable via `provenex policy hash` |
| Receipt archive | The directory of signed receipts for the period under review |
| Public key (for Ed25519-signed receipts) | Published once by the producing org |
| Reference verifier | [`docs/regulator_verification.md`](../regulator_verification.md), ~25 lines pure stdlib |
| Conformance check | `provenex selftest` against the binary on the challenger's own machine |

The challenger reproduces every check independently. No callback to the producing organisation is required.

## What this mapping does not cover

- **Operational and reputational risk** (II.4) is a business-level judgement, not an evidence stream.
- **Capital implications** for the use of an AI agent are out of scope.
- **Inference-quality validation** (whether the LLM gave a faithful answer to the user) is upstream of admission and not addressed by receipts. SR 11-7 calls this out; Provenex receipts pair with an output-grounding or faithfulness layer to cover it.

For the cryptographic verification path, see [`docs/regulator_verification.md`](../regulator_verification.md). For the trust model, see [`docs/threat_model.md`](../threat_model.md).
